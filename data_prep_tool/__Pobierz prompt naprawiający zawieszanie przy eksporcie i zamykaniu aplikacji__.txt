GITHUB COPILOT TASK: FIX GUI FREEZE AND SAFE APPLICATION SHUTDOWN AFTER REPORT EXPORT

Work in the current repository after legacy cleanup. This is a focused bug fix. Do not redesign the application, comparison algorithm, report appearance, workbook data, or project structure.

OBSERVED BUG
After the comparison finishes and the user chooses where to save the Excel deviation report, the application appears to wait indefinitely. The window cannot be closed normally. Clicking the X causes Windows to display that the program is not responding.

LIKELY TECHNICAL CAUSE TO VERIFY
The comparison itself already runs in a worker thread, but ReportGenerator.generate(...) is still called synchronously from CompareTab on the Tkinter main thread after the save dialog. Generating and saving a report with thousands of rows, tables, styles, borders, and conditional formatting can take a noticeable amount of time. While this method runs, Tkinter cannot process redraw events or the window-close event, so Windows classifies the application as unresponsive.

Do not assume this is the only cause. Add timing logs around comparison completion, report workbook construction, workbook.save(), workbook.close(), queue delivery, and GUI session cleanup. Verify the actual blocking stage before finalizing the fix.

Add message types equivalent to:

Add a pure worker entry point equivalent to:

3. COMPARETAB STATE MACHINE
Refactor CompareTab conservatively so the long operation has explicit states:
- idle
- comparing
- awaiting_save_choice
- saving_report
- closing_requested

An Enum is acceptable if it improves clarity. Do not create a generic state-machine framework.

Replace ambiguous duplicated booleans where possible with one authoritative operation state. The Generate button must be disabled during comparing and saving_report, and enabled only when returning to idle.

Required flow:
1. User starts comparison.
2. Comparison worker runs.
3. Main thread receives ComparisonWorkerSuccess and updates preview/summary.
4. Main thread displays askyesno and asksaveasfilename.
5. If user cancels saving, return cleanly to idle.
6. If user selects an output path, start report-save thread and return immediately to Tkinter mainloop.
7. Main thread polls the report queue with root.after(100, ...).
8. Progress updates the status label.
9. Success updates output path, elapsed time, status, and shows success message.
10. Failure shows a typed error and returns to idle.
11. Session cleanup happens exactly once.

Do not call _finish_comparison_session before report saving has completed. Rename the cleanup method to reflect all background operations, for example _finish_operation(). Ensure there is only one code path that restores the Generate button and clears thread/queue references.

4. SAFE WINDOW CLOSE HANDLING
Register one WM_DELETE_WINDOW handler on the root window, preferably in MainWindow because it owns the root. The handler must ask CompareTab whether a background operation is active.

Implement a small public UI method on CompareTab, for example:
- has_active_operation() -> bool
- request_shutdown(on_ready: Callable[[], None]) -> None

Required close behavior:

A. If idle:
- destroy the root immediately through the normal close path.

B. If comparison is active:
- show one confirmation dialog on the main thread:
  "A workbook comparison is still running. Closing now will stop waiting for the result. No source workbook will be modified. Close the application?"
- if user selects No, keep the application open;
- if user selects Yes, mark closing_requested, disable user controls, stop scheduling new UI work except queue polling, and wait for the worker to finish its current cleanup;
- because the comparison thread is daemonized and openpyxl work is not safely cancellable mid-read, do not attempt forced thread termination;
- when the worker posts a terminal success/failure event, discard normal preview/dialog work, perform cleanup, then call on_ready to destroy the root;
- add a bounded fallback timeout only for UI shutdown, for example 5 seconds. After the timeout, destroy the root without calling os._exit. Document that daemon workers terminate with the process. Do not block the Tkinter thread while waiting.

C. If report saving is active:
- do not immediately destroy the process because this can leave a partial .xlsx file;
- show one confirmation/information dialog:
  "The report is currently being saved. The application will close when saving finishes."
- set closing_requested;
- disable controls;
- keep polling the queue;
- when save succeeds or fails, perform cleanup and destroy root without showing additional modal dialogs;
- do not use a short forced-close timeout while workbook.save is active. Protect file integrity.

D. Avoid repeated dialogs:
- if closing_requested is already true, a repeated click on X must not create another messagebox;
- status should become "Closing after the current operation finishes...".

5. REPORT GENERATOR RESOURCE SAFETY
Verify ReportGenerator.generate closes its newly created Workbook in finally.

Required pattern:
- workbook: Workbook | None = None before try;
- create workbook;
- build sheets;
- save;
- return output path;
- except wraps errors in ReportGenerationError with `raise ... from exc`;
- finally closes workbook if it exists;
- if close itself fails, log at DEBUG and do not hide the original exception.

For additional output safety:
- save the report to a temporary sibling path in the same destination directory, with an .xlsx extension;
- after workbook.save(temp_path) succeeds and workbook is closed, atomically replace the requested output with os.replace(temp_path, output_path);
- if generation/save fails, delete the temporary file if present;
- do not write directly over the final report during construction;
- preserve the final filename selected by the user.

Because openpyxl identifies format from the extension, the temporary file must end with .xlsx.
